## Prospective remedy — future launches only

The fixed runner now calls `prune_checkpoints` only for new restart checkpoints.
Immediately before each deletion it hashes the actual on-disk file, requires a
match to the write-time index, and appends a JSON record to the run directory's
`pruning.jsonl` with `path`, deletion-time `sha256`, checkpoint `step`, UTC
`timestamp`, and `event: pre_unlink`. It flushes and fsyncs the receipt before
unlinking; disk-guard, hash, or receipt-persistence failure prevents that deletion.
Best/latest are retained and original checkpoints are outside the pruning glob.

A `pre_unlink` receipt attests verification and durable deletion intent, not
successful unlink: a crash/unlink failure after the receipt can leave the file
present. This ordering avoids an unreceipted deletion if receipt persistence
fails. It is not an adversarial concurrent-file-mutation guarantee. There is
no synthetic historical pruning stream for the running process.
