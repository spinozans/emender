# Triton scoring works; immediate per-session dispatch does not pass the serving gate

**Keep the scorer and asynchronous reader behind switches, not as the new default.** Across 30 cells, the program arms generated identical bytes and issued identical per-document instructions, operands, keys and outcomes. The ready loop acknowledged **154 other bytes during native positional-worker calls** at B16. But under sampled routing it broke 128 backbone batches into **755**, and 764 small-controller batches into **3,399**. On greedy traffic it had no positional stalls to hide. It did not earn the registered 20% throughput gain in either mode. Do not read training throughput into these generation numbers.

## What ran

[Protocol](TRITON_SERVING_PROTOCOL.md) `49e587268`, frozen source `cf0c78501`, [55 CPU gates](receipts/memory-program-s1/qualification.txt). A new [Triton operand scorer](../../../ndm/memory_program/triton_operands.py) gathers each legal candidate's one or two embeddings and addressed page feature, dots with that document's pointer, adds the selected prior, and writes to a masked ragged logit row. Only the chosen vector is materialized to condition the next decision. First VJP recomputes the vector and atomically adds to repeated addresses. No query is fired by a GPU scoring lane. The [ready engine](../../../ndm/memory_program/serving.py) groups compatible ready decisions; a session can suspend on a **chosen**, immutable, key-only lookup. Native positional I/O is serialized on its own lane; the shared short m20 traversal has a separate lock. All numeric values and live reads/writes stay on the main thread. Unfinished frames never publish a write; a per-client valid emit is not rolled back if another client later fails. These are bound local sessions, not a multi-tenant server.

[Device gates](receipts/memory-program-s1/attempt1/device-parity.json): score/first-gradient max abs errors `9.54e-7/3.10e-6`; 103 opcode/operand distributions within `1.20e-6`; delayed writer adjoint norm `0.1461`, error `1.12e-8`. Independent ready-vs-reference replay compared all 16 produced page bindings, masses, tokens, statuses and all 35 parameter adjoints, including an earlier write's later-loss gradient. CPU latch witness requires the fast stream to emit a **second byte before** a slow read can return; no sleep-time inference. Resident **forward only**, 16 owners/297 legal candidates/D48, 64 warm synchronized samples: eager 202.0 µs p50, Triton 130.4 µs. This does not measure the CPU descriptors, the controller or substring search.

Real autoregressive continuation, not teacher forcing: each block opened SHA-checked W3 TRAIN 32-byte prompts with empty cells and generated 64 actual argmax bytes per session. Frozen FP32 C14, full visible-prefix recomputation without KV caching; P2 step-1 checkpoint and eight version-bound readers. Greedy controller in fact only issued `SLICE/LOOKUP/EMIT`; fresh categorical choices also exercised joins, writes, recalls and positions. Indexed independent uniforms keep sampled choices comparable across batch order. Direct uses fixed C14 + longest-positive archive/live branch backoff, **not** W3's trained head and not the same predictor. Independent mount caches per cell; mapped files/OS not cold. B1 used two different prompts across blocks; B16 used 32. 17,280 total generated bytes across arms, including repeated workloads; not a quality dataset. No optimizer, dev/confirmation or scale training.

**Attribution.** In sampled B16 block 0, eager and barrier Triton did the same 52,519 LF steps. The existing worker took **12.182 s** for eager vs **1.183 s** later for Triton. In block 1 they did 5,059 steps, 0.137 vs 0.133 s. The aggregate 2.45× ratio is **not a 2.45× kernel speedup**. By contrast, B16 greedy had zero native positional calls and barrier Triton was ~1.00× eager. Ready-vs-inline actually overlapped I/O (154 vs 0 responses during the worker), but both issued far more small batches. **Next engineering decision:** batch together all clients ready for a backbone byte or memory round, yielding to a genuinely blocked reader rather than eagerly launching a tiny new backbone call on every early emit. Preserve isolation, per-stream causality and actual overlap. For large backbones, provide per-session incremental state instead of full-prefix re-encoding. Price both separately: improving attention on the host cannot by itself remove native locator stalls or Python/controller fences.
