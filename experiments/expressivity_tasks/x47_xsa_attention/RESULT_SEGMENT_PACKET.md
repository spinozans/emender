# Short-segment feature extraction was ~5× faster, but missed the wide update gate by one parameter

**Do not promote it as an interchangeable producer across sizes.** On the retained 150M host, the causal short-segment recorder met both extraction and downstream update tolerances. On the replicated dense 2.22B geometry, the same method passed feature, argmax, executed-program, loss, gradient and AdamW-moment checks, but **one** of the 288,987 updated *policy* parameter elements exceeded its elementwise bound. The failing element was `host.weight[0,158]`, the small controller's host projection, **not** a change to the frozen 2B trunk. Serial/segment updated values −.02276021 / −.02278693 (absolute difference **2.67234e−5**, permitted ~2.046e−5); pre-clip gradients −1.751e−7 / −1.644e−7. Rounded all-byte loss or an unchanged argmax would miss this. No retry or tolerance change.

Rates include producing/assembling the full tables, host copy, checksumming and atomic publication, not host/recorder preparation or learner time. Including recorder preparation/cleanup the segment/serial ratios were .177/.200. Both **price gates passed**. The 2,048 payload bytes per position and private storage costs do not disappear. This is for known, verified **teacher-forcing inputs**, not a decoder for unknown future bytes.
