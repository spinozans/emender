# The frozen serving features reproduced; the post-release **update did not**

**T4 failed the registered exact-update gate.** A separate CUDA-invisible process loaded the retained 150M packet, ran a fresh sampled 4,096-target dense workbench rollout and took an AdamW step. Its input features, every 256-way byte vector, all 4,096 joint selection scores, all 32 per-document event digests, native dispatch, NLL, surrogate and pre-clip gradient norm matched the coupled CPU learner. But **2 of 35 gradient tensor hashes differed**: `embed.weight` and `query.weight`. The updated weights and optimizer state hashes differed too. Hashes cannot say how far the tensors differed or what caused it. Don't substitute a tolerance, report exact training parity, or claim that the 2B offline step ran: the learner stopped at this first mismatch.

**What did pass:** record a frozen FP32 eval host's actual causal hidden[:256] and normalized byte log probabilities, supplying *one* observed byte per invocation, in two blocks of 16 reset documents. Each geometry's separately stopped 63-byte stream matched its 128-byte stream at **all 516,096 tested prefix elements bitwise**. Independent stock 1/31/63 comparisons and the S10-style two-segment endpoint at 128 had maximum error 3.82e−6; argmax matched, slots scrubbed. The coupled learner and the subsequent independent full regeneration had identical feature hashes for *each* model. This is a different encoder from T3's vetoed BF16 training chunk.
